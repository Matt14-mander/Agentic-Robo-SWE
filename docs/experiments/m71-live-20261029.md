# M7.1：首轮 8 题四组真实模型消融

日期：2026-10-29（Asia/Shanghai）。8 道公开 C++ 合成题，每题每组一次有效模型尝试，
四组均为 **8/8（100%）**。这轮没有观察到领域文档、专业工具或开发反馈带来的成功率增益；
总 token 分别为基础组的 **1.00×、1.21×、2.11×、2.56×**。
这是出现天花板效应的公开开发基线，不能据此证明工具无用或真实缺陷泛化已解决。

## 协议、模型与执行范围

- 配置仍为 `deepseek:deepseek-chat:temperature=0`，没有更换模型配置。
  实际 159 次响应均返回 `deepseek-flash`，`system_fingerprint` 均为
  `bc19ba97cbe016479903222bb1578db6`。请求别名不能写成旧版 DeepSeek 的性能结果；
  该指纹也不是可下载、可复现的权重版本。
- 单次预算保持 8 次模型调用、12 次工具调用、16,000 总 token、300 秒；
  每次输出仍限制至多 2,048 token。总 token 仍按调用返回后的 usage 检查。
- Windows、Python 3.13.2、g++ 13.2.0，`--trusted-local` 原生执行；
  每个候选独立编译，28 个公开样例判分。模型仅接触分组允许的工具。
  本轮没有 Docker 隔离、独立隐藏集或真实仓库任务。
- 主段 `repeats=1, seed=0`；最后一题在首次校准时被阻断，另有补跑段，详见下节。
  最终判分仍发生在 worker 和开发轨迹关闭之后，没有向模型反馈最终判分后重试。
- 只为实验进程移除了不可写的 `SSLKEYLOGFILE` 调试设置；成功运行保留宿主原有
  ASCII 临时目录。API 请求在获准的联网执行环境中进行。

原始结果保存在 `.agent_state/ablation-live-20261029-r1-valid/` 和
`.agent_state/ablation-live-20261029-r1-recovery/`。可提交的脱敏分析为

## 校准异常与补跑边界

1. 首次启动 `.agent_state/ablation-live-20261029-r1/` 将 TEMP/TMP 指向中文路径，
   MinGW 汇编阶段无法创建临时文件，8 题均未通过校准，**没有调用模型**。
   相对 TEMP 的单题预检也失败；恢复宿主原生临时目录后，单题四组 smoke 全部通过。
2. 正式主段前 7 题校准及 28 次真实修复通过。最后的 `cpp_anti_windup` 参考解
   曾非零退出，只写出 19/28 行观察，原报告保留 `runtime_error`，四个槽位保留
   `invalid_baseline`，**该题尚未调用模型**。当时适配器未保存运行退出码，
   stderr 为空，因此无法确认根因，不能归因于模型或断言是哪类宿主故障。
3. 同一参考程序复跑正常退出，产生 28 行且独立判分通过；补跑段又重新编译、
   校准 broken/reference 后才执行该题四组，4/4 成功。
   `--case cpp_anti_windup --seed 3` 保持原定组序 `feedback → base → docs → tools`。
   两段环境、题目、起始源码、预算一致，但协议 ID 不同，合并摘要明确保留两段来源。

合并器只允许填补“未校准、无模型响应、无开发轨迹”的槽位，拒绝替换已执行的模型失败。
因此有效模型尝试是 **28 + 4 = 32**，不是从多次修复中挑选最好结果。
首次主段原始成绩仍为每组 7/7 有效修复、另有 1 个校准阻断；合并后才是每组 8/8。

宿主并非专用性能机，运行期间还执行了短时离线测试；这些是观测墙钟，不是纯模型延迟或稳定性能排名。

## 失败分类与轨迹审计

- **最终修复失败：0/32**。没有最终编译/运行/数值失败、预算耗尽、超时、模型错误或无效用量。
- **中间工具错误：1 次**。tools 组的抗积分饱和补丁首次精确匹配失败，记录为 `tool_error`；
  模型在同一次预算内重新提交补丁并通过最终验证，没有操作者追加修复尝试。
- **中间数值失败：6 次**，均为 feedback 组在修改前调用开发验证器复现原缺陷，
  分类为 `numerical_mismatch`；之后各题开发验证均通过。合计 14 次开发验证：6 失败、8 通过。
  这些是有价值的开发反例，不是 6 次最终修复失败，也不能据此算出技能迁移收益。
- **校准阻断另计**：中文临时路径启动失败，以及主段抗积分饱和参考解异常退出，
  均保留原始记录，不进入有效模型修复失败分母。
- 32 份有效轨迹、**1,113 条事件**全部通过离线审计：协议/源码身份、最终判分源码、
  worker/轨迹 token 一致；无截断尾行、未结束节点或缺失源码，开发验证只出现在 feedback 组。
  159 次响应均带用量及缓存明细；32 个最终响应均正常 `stop`，未出现长度截断。
  轨迹记录累计约 6.54 秒，已计入尝试墙钟。
- 轨迹仍为开发证据，`skill_eligible=false`；没有自动提炼或晋升 RepairSkill。

## 解释与下一步

1. **本轮无法支持成功率提升结论。** 任务提供精确目标文件、明确契约与故障线索，
   主要是小型单文件修复；基础组已经全部通过。按 case bootstrap 得到的 `[1,1]`
   是全成功小样本的退化区间，不是“真实成功率确定为 100%”，也不能证明四组等效。
2. **领域说明增加上下文，但没有改变本轮通过率。** docs 与 base 均为每题 4 次模型响应、
   3 次工具调用；docs 总 token 高 20.9%。专业工具和反馈组分别高 111.2%、155.6%。
   本轮支持“额外能力有成本”的观察，不支持普遍移除这些能力。
3. **反馈的已证实价值是开发证据闭环。** 六题保留了修复前失败与修复后通过；
   这可作为 M8 技能候选的来源，但还缺独立准入回归、负例和跨任务迁移验证。
   D 组开发与最终判分仍使用同一公开样例，无法检验针对反馈的过拟合。
4. **M7.1 下一项 P0**：记录原生运行退出码并复查参考程序运行稳定性；增加独立开发/保留划分，
   固定 Linux 环境接入其余 9 道重依赖题，提高任务区分度。不能事后修改这轮题目或预算抬分。
5. **P1**：在冻结协议下追加重复轮次以测量随机性，并推进 M7.2 真实仓库、多文件和未知定位任务。
   若服务端指纹或运行环境改变，单独分层报告；避免把同一简单套件的大量重复当成新任务证据。
